# Material 3 Expressive — React Native Implementation Guidelines

Generated by Claude.

Purpose: give an AI coding assistant (or a human dev) a concrete, checkable spec for building React Native UI that follows Google's Material 3 Expressive (M3E) design language. Treat every section as a rule set, not inspiration — when a component is built, check it against the relevant section before calling it done.

This design is to be implemented throughout the launcher -- except in the Vade Mecum mini-app. DO NOT implement material design in Vade Mecum.

---

## 0. What M3E actually changes vs. classic Material 3

M3E is not a new color picker skin. It's a research-backed evolution (Google ran 46 studies, 18,000+ participants) built on five levers: **color, shape, size, motion, and containment**. The core claim, and the reason to take it seriously rather than treat it as decoration: applied correctly, users locate the right element faster and complete tasks faster than on flat/classic Material — the visual "loudness" is functional, not cosmetic.

Concretely, versus classic Material 3:
- Shape becomes a first-class expressive tool (35 abstract shapes, 10-step corner radius scale), not just "rounded corners = friendly."
- Motion uses physical springs, not duration/easing curves.
- Containment (grouping elements in bounded, colored regions) replaces whitespace-only separation as the primary way to signal structure.
- Type scale and component sizes got more variety (more size steps per component, "flexible" app bar variants, etc.).

**Guiding rule for the AI:** every use of color, shape, or motion should be answering "what does this tell the user about structure or interactivity?" If it can't answer that, it's decoration and should default back to the neutral/baseline treatment.

## 1. Color system

### 1.1 Token structure
Don't hardcode hex values in components. Build a token file with these roles (this is the M3 color role system — implement all of them even if a given app only visibly uses a subset):

```
primary, onPrimary, primaryContainer, onPrimaryContainer
secondary, onSecondary, secondaryContainer, onSecondaryContainer
tertiary, onTertiary, tertiaryContainer, onTertiaryContainer
error, onError, errorContainer, onErrorContainer
surface, onSurface, surfaceVariant, onSurfaceVariant
surfaceDim, surfaceBright
surfaceContainerLowest, surfaceContainerLow, surfaceContainer,
surfaceContainerHigh, surfaceContainerHighest
outline, outlineVariant
inverseSurface, inverseOnSurface, inversePrimary
```

### 1.2 Dynamic color
- Generate the full palette from a single seed color (brand color, or user/device wallpaper color on Android 12+) using an HCT-based algorithm — don't hand-pick tonal steps. Use `@material/material-color-utilities` (works in RN/JS) to derive tonal palettes and both light/dark schemes from one seed.
- Support light and dark scheme objects generated from the same seed; never maintain them as two independently hand-tuned palettes.
- Where the OS exposes a user wallpaper/theme color (Android), wire it in as the seed if the app wants a personalized (not just branded) theme. This is optional — a fixed brand seed is a valid, common choice.

### 1.3 Applying color: signal, don't decorate
- Use **stronger/saturated fills** only on primary interactive elements (main CTA, selected state, active tab). This is the single highest-leverage change from flat design: a filled, contrasting button should visually win against a page of low-contrast text.
- Use `*Container` roles (e.g. `primaryContainer`) for secondary-emphasis interactive surfaces — chips, secondary buttons, selected list rows.
- Use `surfaceContainer*` steps to create layered depth between a screen background and cards/sheets sitting on it, instead of only using elevation/shadow.
- Never rely on color alone for meaning — pair with shape/icon for accessibility (WCAG — don't make "selected vs not" color-only).

## 2. Shape system

### 2.1 Corner radius scale
Implement a shared shape-token scale, don't invent per-component radii:

| Token | Radius |
|---|---|
| none | 0dp |
| extraSmall | 4dp |
| small | 8dp |
| medium | 12dp |
| large | 16dp |
| largeIncreased | 20dp |
| extraLarge | 28dp |
| extraLargeIncreased | 32dp |
| full | 9999dp (pill/circle) |

Map components to a default token (buttons → `full` or `large`, cards → `medium`/`large`, sheets → `extraLarge` top corners, FAB → `large`/`full` depending on size). Keep this mapping in the token file so the AI/devs pick a token name, never a raw number.

### 2.2 Principles to enforce
- **Shape is not semantic.** Don't assign one shape a fixed meaning ("wavy = loading only"). The same shape family can recur across a loading indicator, a button container, an avatar mask — that's intentional visual cohesion, not a bug to "fix."
- **Embrace tension deliberately, sparingly.** Combining a sharp/angular container with soft rounded children (or vice versa) is a valid, spec'd technique for drawing the eye — but use it for one or two focal elements per screen, not globally. If everything is "tense," nothing is.
- **Abstract/organic shapes (the 35-shape library) are decorative accents only** — avatars, image crop masks, empty-state graphics, loading indicators. Never use an abstract blob shape as a tap target or content container; interactive containers stay on the corner-radius scale above.
- **Shape morphing** on state change (square→circle on selection, blob morph on loading) should use the motion spring system (§3), not a linear/duration-based transform.

## 3. Motion

### 3.1 Use springs, not durations
M3E motion is physics-based (mass/stiffness/damping), not `duration + easing curve`. In React Native, implement with `react-native-reanimated`'s `withSpring`, not `withTiming`, for anything state-driven (press, selection, expand/collapse, shape morph).

Baseline spring presets to define once in a motion tokens file and reuse everywhere (tune damping/stiffness by feel, but keep these three tiers distinct):

```js
export const motionSprings = {
  // small, local UI feedback: press states, toggles, icon morphs
  expressiveFast: { damping: 20, stiffness: 300, mass: 0.6 },
  // medium: card expand, sheet open, FAB morph
  expressiveDefault: { damping: 18, stiffness: 180, mass: 0.8 },
  // large: full-screen transitions, shared-element transitions
  expressiveSlow: { damping: 22, stiffness: 120, mass: 1 },
};
```

### 3.2 Where motion is required, not optional
- Any state change on an interactive element (press, select, toggle, error) needs a spring-driven transition — scale, color, or shape. A dead instant state-flip reads as "broken" against M3E's spec, not neutral.
- FABs, chips, and buttons should have a subtle press-scale (~0.95) with `expressiveFast`.
- Loading indicators should use continuous shape-morph animation (not a static spinner) where the component supports it.
- Screen/route transitions: use shared-element or container-transform patterns (e.g. via `react-native-shared-element` or Reanimated's layout animations) rather than plain fade/slide when navigating from a list item into its detail view — this is a signature M3E pattern (container transform).

### 3.3 Respect reduced motion
Always branch on the OS "reduce motion" accessibility setting (`AccessibilityInfo.isReduceMotionEnabled`) and fall back to opacity/instant transitions. Never skip this to "keep it expressive" — accessibility settings override style guidelines, full stop.

## 4. Typography

Implement the full type scale, five roles × three sizes = 15 styles. Don't invent ad hoc font sizes in components.

| Role | Small | Medium | Large |
|---|---|---|---|
| Display | 36/44 | 45/52 | 57/64 |
| Headline | 24/32 | 28/36 | 32/40 |
| Title | 14/20 | 16/24 | 22/28 |
| Body | 12/16 | 14/20 | 16/24 |
| Label | 11/16 | 12/16 | 14/20 |

(sizes/line-heights in dp; treat as defaults — brand font pairing and exact numbers can be tuned, but keep 5 roles × 3 sizes as the structure.)

Rule: pick type roles by **hierarchy position**, not by "what looks about right" — e.g. screen title = `titleLarge` or `headlineSmall`, list item primary text = `bodyLarge`, list item secondary text = `bodyMedium`/`labelMedium`, button label = `labelLarge`.

## 5. Containment & layout

This is the most under-implemented M3E principle and the one with the biggest measured usability effect (faster correct-element fixation, faster task completion vs. flat design) — prioritize it.

- **Group related interactive elements in a shared rounded container with a distinct background** (a `surfaceContainer*` fill) rather than separating them with whitespace and a text label alone. E.g., a settings section: don't just put a heading and then flat list rows on the screen background — wrap the rows in one rounded container.
- Use **subtle background-color dividers between items inside a shared container** (not full-width `<View>` border lines) to distinguish items while preserving the "this is one group" signal from the container's outer boundary.
- **Contrast interactive surfaces against their background deliberately.** A button or input sitting directly on the screen background with no fill/border is the flat-design failure mode this whole system was built to fix — give it a container.
- Adopt M3's **adaptive layout patterns** for larger screens/tablets/foldables if the app targets them: canonical layouts (list-detail, supporting-pane, feed) rather than one fixed phone layout stretched wide. For a phone-only RN app this is lower priority — note it, don't over-build it.

## 6. Component sizing

M3E expands most components from 1 size to a small set of size steps — implement as a `size` prop, default to the mid step:

- **Buttons:** support at least `small` / `medium` (default) / `large` height steps; increase corner radius token as size increases (e.g. small → `large` shape token, large → `full`).
- **FAB:** support `small`, `default`, `large`, and `extended` (icon + label) variants — don't hardcode one FAB size across the app.
- **App bar:** implement both baseline **and** the newer **flexible** medium/large variants (flexible = title area that reflows/resizes on scroll, not a fixed baseline height) — prefer flexible for primary screens per current M3E spec.
- **Progress indicators:** support the M3E segmented/wavy variants in addition to the plain linear/circular ones for long-running or playful contexts (e.g. onboarding, sync).

## 7. Libraries & setup in React Native

- **Primary recommendation: `react-native-paper` (v5+).** It implements MD3 tokens, theming, and most components. Caveat to bake into the plan: as of this spec, Paper's M3 Expressive coverage is **partial and in progress** upstream — some flexible app bar variants, scroll-reactive elevation, and a few size/anatomy details from the M3E spec aren't fully implemented yet. Check the installed version's changelog/open issues before assuming a specific M3E behavior (e.g. flexible top app bar) is available out of the box; build a thin custom wrapper for any gap rather than fighting the library.
- **Motion:** `react-native-reanimated` (springs, layout animations, shared element-style transitions) + `react-native-gesture-handler` for press/gesture-driven state.
- **Shape/vector needs** (abstract decorative shapes, custom morphing icons): `react-native-svg`, animated via Reanimated.
- **Color generation:** `@material/material-color-utilities` (pure JS/TS, works in RN) to derive tonal palettes from a seed color — don't hand-roll HCT math.
- Build one central `theme/` module: `colors.ts` (generated tokens, light+dark), `shape.ts` (radius scale), `type.ts` (type scale), `motion.ts` (spring presets). Every component imports from these — no inline magic numbers for color, radius, font size, or animation config anywhere else in the codebase.

## 8. Implementation checklist

Use this as a per-component/per-screen review gate:

- [ ] All colors come from theme tokens (no hardcoded hex)
- [ ] Corner radius uses a shape token, not a raw number
- [ ] Type uses one of the 15 defined text styles
- [ ] Interactive state changes (press/select/toggle) animate via a spring preset, not `withTiming`/CSS transition
- [ ] Reduced-motion setting is checked and respected
- [ ] Related controls are grouped in a shared container with background fill, not just whitespace
- [ ] Primary action per screen has visibly stronger color contrast than secondary actions
- [ ] Component supports size variants where the M3E spec defines them (buttons, FAB, app bar)
- [ ] Both light and dark theme render correctly from the same seed color
- [ ] Touch targets meet minimum size (48×48dp) regardless of visual size

---

## 9. Anti-patterns to reject

- Rounding every corner to the same large radius everywhere ("rounded = expressive") — radius should vary meaningfully by component role and hierarchy.
- Using an abstract/organic shape as a button or tappable container.
- Adding springy motion to *every* micro-interaction indiscriminately — it should emphasize state changes, not turn into constant jiggle.
- Flat, unfilled buttons/inputs sitting directly on the background with no container — this is the exact flat-design pattern M3E's containment principle replaces.
- Treating this doc as final visual design — it's a rule set for *implementing* a design that should still be art-directed (brand seed color, illustration style, copy) by whoever owns the product's look.


## Current Issues (remove section when fixed)

1. No spring-based motion anywhere — the biggest gap
The header comment claims "OFFICIAL MATERIAL 3 EXPRESSIVE SPECIFICATION," but there's no react-native-reanimated import and no spring animation at all. Every "press" effect is just:

js
transform: [{ scale: pressed ? 0.98 : 1 }]

on the raw Pressable pressed boolean — that's an instant snap between two states, not the physics-based spring transition M3E is built around. This is the one thing that most defines "Expressive" motion, and it's entirely absent. Worth wiring withSpring on press-in/press-out for the button/chip/nav components at minimum.

2. Type scale is over-bolded relative to spec
Official M3 weights are Regular (400) for Display/Headline/Body and Medium (500) for Title/Label. This file uses 700 for Display and Label, 600 for Title/headlineSmall. That's not a small stylistic tweak — it flattens the weight-based hierarchy the scale is designed to carry (size and weight normally do different jobs), and it'll look visually inconsistent next to actual system M3 UI. 

3. Hardcoded hex colors bypass the token system
hoursToM3Color returns raw 
#34A853 / 
#81C995 for the fasting bar chart — these don't exist in m3Light or m3Dark at all, so they won't adapt between light/dark mode and there's no way to retheme them. Should be real token roles (e.g. a success/tertiary pair with light/dark variants), same as everything else in the file.

4. Shape scale values don't match what the comment claims
large: 20, extraLarge: 32, extraExtraLarge: 48 vs. the actual M3 spec values (large: 16, extraLarge: 28). 

5. Touch targets on the chart are too small
The weight-chart Circle points use r={mappedPoints.length > 30 ? 3 : 5} with onPress directly on the SVG circle — that's a 6–10dp tap target, well under the 44–48dp minimum, and there's no hitSlop-equivalent for SVG shapes. Real devices will make these very hard to hit precisely.

6. Card styling mixes two M3 surface treatments
M3Card always applies both a surfaceContainer* fill and a 1px outlineVariant border. M3 normally treats "filled/elevated" (tonal fill, no border) and "outlined" (border, minimal fill) as distinct card variants — combining both on every card blurs that distinction and reads heavier than either variant alone.

/**
 * M3 Expressive palette generator.
 *
 * Replaces hand-authored m3Light / m3Dark hex objects with palettes derived
 * from a single seed color, using Google's own color-science library. This
 * guarantees light/dark stay tonally consistent and gives you a legitimate
 * "success" role (for things like the fasting-duration chart) that's
 * harmonized with your brand color instead of a bare hardcoded green.
 *
 * npm i @material/material-color-utilities
 *
 * Note: this package's ESM build omits file extensions on its internal
 * imports, which strict Node ESM resolution rejects. It resolves fine under
 * Metro (React Native's bundler) and under webpack/esbuild — you only hit
 * the error if you try to run it directly with plain `node`.
 */

import {
  Hct,
  SchemeExpressive,
  MaterialDynamicColors,
  customColor,
  argbFromHex,
  hexFromArgb,
  type CustomColorGroup,
} from '@material/material-color-utilities';

// The full role set your app already uses (matches the shape of the
// original m3Light/m3Dark objects) plus a `success` group added on top.
export interface M3Theme {
  primary: string;
  onPrimary: string;
  primaryContainer: string;
  onPrimaryContainer: string;
  inversePrimary: string;

  secondary: string;
  onSecondary: string;
  secondaryContainer: string;
  onSecondaryContainer: string;

  tertiary: string;
  onTertiary: string;
  tertiaryContainer: string;
  onTertiaryContainer: string;

  error: string;
  onError: string;
  errorContainer: string;
  onErrorContainer: string;

  background: string;
  onBackground: string;
  surface: string;
  onSurface: string;
  surfaceVariant: string;
  onSurfaceVariant: string;
  inverseSurface: string;
  inverseOnSurface: string;

  surfaceDim: string;
  surfaceBright: string;
  surfaceContainerLowest: string;
  surfaceContainerLow: string;
  surfaceContainer: string;
  surfaceContainerHigh: string;
  surfaceContainerHighest: string;

  outline: string;
  outlineVariant: string;
  scrim: string;

  // Harmonized custom role — replaces the hardcoded #34A853 / #81C995
  // greens used for "fasting achieved" states. Blended toward the seed so
  // it never clashes with the rest of the palette, however the brand color
  // changes.
  success: string;
  onSuccess: string;
  successContainer: string;
  onSuccessContainer: string;
}

// Every M3 dynamic-color role name we pull from MaterialDynamicColors.
const ROLE_KEYS = [
  'primary', 'onPrimary', 'primaryContainer', 'onPrimaryContainer', 'inversePrimary',
  'secondary', 'onSecondary', 'secondaryContainer', 'onSecondaryContainer',
  'tertiary', 'onTertiary', 'tertiaryContainer', 'onTertiaryContainer',
  'error', 'onError', 'errorContainer', 'onErrorContainer',
  'background', 'onBackground', 'surface', 'onSurface',
  'surfaceVariant', 'onSurfaceVariant', 'inverseSurface', 'inverseOnSurface',
  'surfaceDim', 'surfaceBright',
  'surfaceContainerLowest', 'surfaceContainerLow', 'surfaceContainer',
  'surfaceContainerHigh', 'surfaceContainerHighest',
  'outline', 'outlineVariant', 'scrim',
] as const;

/**
 * Generate light + dark M3 Expressive themes from one seed color.
 *
 * @param seedHex   Brand/seed color, e.g. '#0B57D0'.
 * @param successSeedHex  The green (or whatever "positive" color) you want
 *                        harmonized into the palette as the `success` role.
 *                        Defaults to a standard Material green.
 */
export function generateM3Theme(
  seedHex: string,
  successSeedHex: string = '#34A853'
): { light: M3Theme; dark: M3Theme } {
  const sourceArgb = argbFromHex(seedHex);
  const sourceHct = Hct.fromInt(sourceArgb);

  // SchemeExpressive is the M3 Expressive scheme variant — wider hue spread
  // between primary/secondary/tertiary than SchemeContent/TonalSpot, which
  // is what gives Expressive themes their more energetic, varied look.
  const lightScheme = new SchemeExpressive(sourceHct, false, 0.0);
  const darkScheme = new SchemeExpressive(sourceHct, true, 0.0);

  const successGroup: CustomColorGroup = customColor(sourceArgb, {
    value: argbFromHex(successSeedHex),
    name: 'success',
    blend: true, // blend toward the seed so it stays in-family
  });

  function buildFrom(scheme: SchemeExpressive, custom: CustomColorGroup['light']): M3Theme {
    const roles = {} as Record<(typeof ROLE_KEYS)[number], string>;
    for (const key of ROLE_KEYS) {
      const argb = (MaterialDynamicColors as any)[key].getArgb(scheme);
      roles[key] = hexFromArgb(argb);
    }
    return {
      ...(roles as unknown as M3Theme),
      success: hexFromArgb(custom.color),
      onSuccess: hexFromArgb(custom.onColor),
      successContainer: hexFromArgb(custom.colorContainer),
      onSuccessContainer: hexFromArgb(custom.onColorContainer),
    };
  }

  return {
    light: buildFrom(lightScheme, successGroup.light),
    dark: buildFrom(darkScheme, successGroup.dark),
  };
}
